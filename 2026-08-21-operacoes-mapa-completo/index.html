01 / ContextoUm técnico, um lugar, um chamado.

Entenda o domínio antes do código. Todo o resto do sistema orbita essa tríade.

O negócio em uma frase

A Eletromidia instala e mantém equipamentos de mídia exterior (paineis, telas, relógios) em ruas, prédios e shoppings. Quando um equipamento quebra ou precisa de manutenção preventiva, abre-se um chamado. Um técnico vai até o place, executa a atividade, responde checklist, tira fotos de antes e depois. O Operações registra tudo isso, controla prazos, calcula produtividade e conversa com sistemas legados e APIs de prefeitura.

O núcleo é o ticket. Models como Place, Establishment, ActivityType, Checklist e Route giram em volta dele. Se você entender o ciclo de vida do ticket, entendeu 80% do domínio.

Quem usa

  • Técnicos em campo, via app mobile autenticado por API (Passport/Sanctum).
  • Backoffice, via painel AdminLTE com Blade e Vue.
  • Gestão, via dashboards, relatórios PDF/Excel e NPS.
  • Sistemas externos, via rotas de API e jobs de sincronização.

04 / DomíniosOs módulos e onde eles moram.

Cada módulo tem rota própria, pasta de controller própria e, nos mais recentes, services dedicados.

Tickets core

O coração. Abertura, atribuição, suspensão com foto e motivo, fechamento em lote via command (timer de 1800s), relatórios pesados. Fluxos de app mobile espelhados em testes N0 a N3, separando street/not-street e preventive/corrective.

PPO recém-mergido

Programa de pontos e recompensas para técnicos. O módulo mais moderno do repo: 10 services nomeados por responsabilidade, campos de status migrados para enums no último refactor, autorização coberta pelo PpoAuthorizationTest e justificativas de review estruturadas com colunas próprias no banco.

Google Sheets sync

Infraestrutura nova de sincronização automática: datasets tipados (Tickets, Technicians, Checklists, Places) com handlers e controle de estado por destino.

Fleet, Checking, Quality

Frota de veículos, conferência de equipamentos e qualidade de execução. Cada um com arquivo de rotas e pasta de controllers.

Posting, Projects, Competitor

Postagem de mídia, projetos de obra com inspeção e roteirização, monitoração de concorrentes. Projects é o segundo maior arquivo de rotas (302 linhas).

Integrações externas

IVC (dados de equipamentos), MunicipalSp (prefeitura de SP), 4yousee, SAML2 para SSO corporativo, Slack para notificações, web-push para alertas no navegador.

Legacy só leitura

routes/legacy.php expõe users, establishments e chamados do sistema antigo. O SQL Server entra aqui: conexão sqlsrv configurada apenas para consultas ao legado.

Radar congelado

Tem controller, teste de boundary de escopo e um HTML solto na raiz. O contexto atual diz: não reviver. Está no backlog de infra, não no roadmap.

05 / FrontendBlade com ilhas de Vue 3, servidas pelo Mix.

Não é SPA. Não é Vite. É Laravel clássico com Vue montado onde faz sentido.

como funciona

A stack real

  • Laravel Mix 6 sobre Webpack 5. Build via npm run development ou production. Node 16.13.
  • Vue 3.2 + Vuex 4. 233 componentes em resources/js/components, stores em resources/js/store.
  • Bootstrap 4 + AdminLTE 3. O layout do painel inteiro depende disso.
  • Bibliotecas de campo: DataTables, Select2, Filepond, FullCalendar, Leaflet, Chart.js, Summernote.
o que esperar

O convívio com o legado

  • jQuery ainda vive aqui. Vem junto com Bootstrap 4 e não vai embora tão cedo.
  • moment.js em vez de dayjs. Já está no package.json, respeite.
  • Vuex, não Pinia. Novo estado entra no store existente.
  • Nunca rode watch/dev/production localmente. Regra do AGENTS.md. O build roda no pipeline.

06 / DadosDois bancos, um dump obrigatório.

MySQL 8 é a verdade. SQL Server é o passado que ainda precisa ser consultado.

MySQL 8 (primário)

Toda escrita acontece aqui. 438 migrations contam a história. Para desenvolver de verdade você precisa restaurar um dump de produção localmente, o README avisa isso explicitamente. Sem dados reais, metade dos fluxos não se comporta como em produção.

SQL Server (legado)

Conexão sqlsrv em config/database.php, usada para ler dados do sistema anterior. Nunca escreva nela. Os controllers Legacy consomem essas tabelas.

Autenticação e filas

Três mecanismos convivem: Passport para os tokens do app mobile, Sanctum para sessões de API mais leves e Socialite SAML2 para o login corporativo. As filas rodam no Horizon, com jobs para fechamento em lote de tickets, sincronizações e notificações push.

07 / Agent-drivenEste repo foi escrito para humanos e agentes.

A especificação dirigida por agentes não é enfeite. Ela define como qualquer IA deve trabalhar neste código.

AGENTS.md: o contrato operacional

Define o papel (senior dev focado em manutenção segura), a compatibilidade (PHP 7.4, nada de sintaxe do 8), performance (evitar N+1, chunk em volumes grandes), o fluxo WSL (editar no Linux real, nunca via PowerShell) e a economia de tokens (comandos curtos, buscas com rg, não reabrir arquivos lidos).

CLAUDE.md: as verdades do repo

A regra número um é forte: evidência atual do repo vence Obsidian, comentários de PR, planos antigos e memória. Notas históricas são pistas, não autoridade. Antes de mudar comportamento, leia os arquivos que hoje o implementam. Também fixa: npm com lockfile, não Bun. PHPUnit, não Pest. Comandos sempre via ./sail.

docs/wayfinder

Mapas de investigação em markdown. O mapa do saIA lista decisões tomadas (analysis grain = 1 ticket, persistência dedicada fora de tickets, cron com janela rolante) e perguntas abertas com tradeoffs explícitos.

graphify-out

Grafos de conhecimento do codebase gerados por data, com GRAPH_REPORT.md. Útil para entender dependências sem ler arquivo por arquivo.

docs/agents/skills

Habilidades específicas do repo, como operacoes-continuous-development, que força verificação no código atual antes de confiar em notas históricas.

08 / saIAA spec está pronta. O código ainda não chegou.

O próximo capítulo do Operações é um harness de análise visual com IA. E ele tem um dos contratos técnicos mais bem escritos que este repo já produziu.

O que a spec garante

  • Seleção determinística. Command horário pega tickets concluídos entre 4h e 5h atrás, janela semiaberta (>= e <) para nunca processar duas vezes.
  • Idempotência por design. UNIQUE(ticket_id) em ticket_analyses. Qualquer análise existente exclui o ticket do cron. Sem flag de force.
  • Reserva transacional. Lock, seleção, criação da run, reserva das linhas e commit antes de despachar qualquer job.
  • Claim atômico no job. analysis_id + expected_run_id precisam bater e o estado precisa ser queued. Entrega duplicada retorna sem efeito.
  • Estados explícitos. queued → processing → completed_dry_run / completed_live / skipped_no_evidence_pair / failed / dispatch_failed. Uma tentativa automática, depois só retry manual via saia:retry-maintenance-analysis.
  • Read-only no MVP. A IA reconstrói evidências (fotos antes/depois/checklists) e apoia a decisão humana. Ela não aprova, rejeita nem encerra chamado.

Onde está hoje

PR #912, draft. Verifiquei direto no repositório: nenhum arquivo saIA, TicketAnalysis ou migration ticket_analyses existe no main. O que existe é a spec em docs/saia/maintenance-analysis-overview.md, validada localmente segundo o próprio documento, esperando revisão de contract e isolamento do banco de testes.

Se alguém te disser que a saIA "já roda", desconfie. Ela roda na cabeça da spec e numa PR fechada. O caminho aberto é: revisar accounting e testes, suíte verde, merge da fundação, e só então prompt builder e live Gemini.

09 / ArmadilhasO que derruba quem chega agora.

Cada item abaixo já custou tempo de alguém. Leia antes do primeiro commit.

PHP 7.4, sem discussão.
Sem enums nativos, sem match, sem constructor property promotion, sem readonly. O composer.json trava platform em 7.4.3. Sintaxe do PHP 8 quebra o build.
compatibilidade
npm, não Bun. Node 16.13.
O ecossistema global do Israel é Bun, mas este repo usa npm com package-lock.json. Respeite o lockfile.
tooling
Tudo via ./sail.
Sem php artisan serve. Sem php local. Artisan, composer, npm e phpunit passam pelo wrapper do Sail.
runtime
Cobertura de testes desigual.
30 arquivos cobrem bem API mobile, PPO e Radar. O painel Blade, com 627 views, quase não tem teste. Mudança em tela admin = teste manual.
atenção
Migrations e índices exigem aprovação.
Regra do CLAUDE.md: nada de dep nova, índice ou migration sem aprovação explícita. 438 migrations já bastam.
gate
WSL é o ambiente real.
O projeto pode abrir por caminho UNC no Windows, mas execução é no Linux. Edite no WSL, valide com git diff no fim.

10 / ComeçandoSeu primeiro dia, em cinco passos.

Do clone ao primeiro diff válido. Nada aqui é opcional.

1

Suba o ambiente

Clone, rode ./setup.sh com Docker ativo. Ele cria .env, instala deps, gera APP_KEY, sobe os containers e roda migrations. Depois ./sail up -d no dia a dia.

2

Restaure o dump de produção

Sem dados reais no MySQL do Sail, os fluxos de ticket não se comportam como em produção. O README deixa isso explícito.

3

Leia os dois contratos

AGENTS.md e CLAUDE.md na raiz. São curtos e salvam horas. Depois leia docs/saia/maintenance-analysis-overview.md para entender para onde o projeto vai.

4

Conheça os atalhos

make help lista tudo: start, stop, migrate, test-db, seed com CLASS=Nome, optimize. O Makefile é o manual de bolso do repo.

5

Valide antes de dizer pronto

git diff no fim, php -l nos arquivos tocados, e os testes do módulo via ./sail php vendor/bin/phpunit. Esse é o fluxo preferido documentado no AGENTS.md.

Por onde entrar no código

Comece pelo ciclo do ticket: routes/web.php → TicketController → TicketRepository → Ticket model. Depois suba um nível e leia Services/Ppo, que mostra o padrão que o código novo deve seguir. Deixe o Legacy e o Radar quietos. E acompanhe a PR #912: quando ela mergear, o main ganha o capítulo mais interessante dos próximos meses.
