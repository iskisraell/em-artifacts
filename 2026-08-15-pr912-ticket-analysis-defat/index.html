02 / A gordura

48 achados em 8 frentes.

Nem tudo é para apagar. Cada frente tem um tipo de trabalho: cortar, minimizar, combinar, deprecar, refatorar, mapear o impacto, reconciliar o conflito, sequenciar.

1 · cortar

Apagar o que sobrou

Métodos sem chamador, testes redundantes, campos que nada lê.

generateContentWithImages(), if/else com dois ramos idênticos, chave api_key morta.

2 · minimizar

Encolher o que é demais

Catch duplicado, rota fora do prefixo, retry que reinventa o padrão.

Adotar $tries = 3 + backoff do Laravel no lugar do classificador próprio.

3 · combinar

Fundir duplicados

Duas fórmulas de status fazendo a mesma conta. Re-scan morto no job.

finalizeIfComplete() contra accountRunProgress() viram uma só fórmula.

4 · deprecar

Renomear, não fundir

Exceções com nome enganoso. Glossário que duplica o catálogo de problemas.

Custo zero em linhas. Só alinhamento de nomenclatura.

5 · refatorar para padrão

Usar o nativo

Trocar raw SQL por Eloquent. Tirar lógica do controller gigante. Mover 170 linhas do job para o resolver.

DB::table vira place.shelterInformation. Em PHP 7.4, optional(), não ?->.

6 · blast-radius

Mapear o impacto

Bundle de JavaScript obsoleto de 124 KB. Fallback com decisão pendente. Restrição única de ticket.

Não commitar public/js/app.js stale. Reverter ou justificar o 'Não informado'.

7 · ppo-merge

Resolver o conflito fatal

PPO #946 apaga ProblemCriticality e adiciona Ticket::problems(). A PR #912 usa o que foi apagado.

Dropar o use ProblemCriticality e trocar problemCriticalities por problems.

8 · sequenciar

Executar em fatias

Cada corte vira um PR pequeno, testado, revisado. Um portão libera o próximo.

Agent loop: pesquisa → implementa → testa → revisão adversária → gate.

03 / As regras

O que o William reprova.

O plano existe para passar nessas regras. Elas não são negociáveis.

As sete regras

  • Regra 1. PR mínimo e nativo.
  • Regra 2. Zero mudanças sem justificativa em superfícies globais.
  • Regra 5. Transações de SQL Server preservadas. Eloquent respeita a lixeira (SoftDeletes).
  • Regra 6. Trava única em migração precisa de justificativa.
  • Regra 7. Helper universal precisa de justificativa.
  • Regra 9. Sem código morto, sem over-abstração, sem reinventar.
  • Regra 10. Reusar o catálogo nativo em vez de hard-code.

Por que importa

Uma PR gorda quebra várias regras de uma vez. Não é opinião de gosto. É o critério que decide se o merge acontece.

O objetivo do plano é chegar a um diff visualmente enxuto, não só tecnicamente correto.

04 / O que não cortar

Cortes que parecem óbvios e quebram.

A verificação adversária pegou seis cortes ingênuos que a primeira passada sugeriu. Todos foram rejeitados.

não cortar

run_items

É load-bearing. O job lê essa tabela para saber a identidade de cada análise e o progresso do lote.

não cortar

Cache::lock

É o único guard contra duas execuções manuais ao mesmo tempo.

não cortar

toGeminiSchema / mapNode

Geram o formato de resposta que o job envia para a IA. Sem isso, a chamada não sabe o que receber.

não cortar

Guard de SSRF

Allowlist de host, caminho, porta e query é defesa contra brecha. Não é reinvenção.

não cortar

related_problem_property

É código de problema, não de antes e depois. Trocar por papel temporal quebraria o domínio.

não cortar

NonRetryable*

As exceções codificam o caminho quieto contra o barulhento. Fundir apagaria essa distinção.

05 / Decisões

O que ficou travado.

Uma entrevista direta, pergunta a pergunta, fechou cinco pontos. Cada um muda o que entra no corte.

1. Destravar primeiro, refatorar depois.
A PR atual recebe o essencial mais os cortes P0. A gordura estrutural vai para uma branch nova.
estratégia
2. Escopo 1 mais 2.
Foco em remover superfície global desnecessária e reduzir over-abstração. Abordagem A.
escopo
3. Uma análise por chamado.
unique(ticket_id) fica e é documentada. A tabela run_items é load-bearing, não redundante.
schema
4. Retry nativo.
$tries = 3 + backoff do Laravel substituem o classificador próprio. Gemini cobra por token, re-cobrar não é problema.
fila
5. Antes e depois vivem dentro de uma análise.
Não são dois registros por chamado. A restrição única não impede o antes e o depois.
design
06 / Visão adversária

Será que faz sentido?

Cinco pontos honestos que podem afundar o plano. Lidos antes de executar, viram salvaguardas.

risco 1

"Depois" vira "nunca"

Refatorar depois só sobrevive se a issue abrir no mesmo dia do merge, com dono e prazo.

risco 2

O nome engana

A PR se chama "Antes e Depois" mas a decisão é uma análise por chamado. Precisa ficar claro que ambos vivem numa análise só.

risco 3

Pode não desbloquear

A queixa central é gordura. Se depois dos cortes o diff ainda parecer gordo, reprova de novo.

risco 4

Processo pesa mais que o código

Para corte pequeno, um ou dois agentes bastam. Não repetir a escala de 17 agentes da análise inicial.

risco 5

Só é seguro com as nuances

Vários cortes que parecem óbvios quebram coisas se feitos isolados. A lista de cortes anda sempre com o "por que não cortar".

O que isso muda

O plano não ignora esses riscos. Cada um vira uma regra de execução: dono no dia do merge, diff enxuto, escala proporcional, nuance sempre junto do corte.

07 / Executar

O caminho em fatias.

Um ciclo de trabalho se repete em cada fatia. Cada fatia vira um PR pequeno e revisável.

O loop

pesquisa (se preciso) → implementa (TDD) → verifica (testes) → revisão adversária → gate

O gate libera a próxima fatia só se

1. suíte verde 2. diff passou na revisão adversária 3. nada load-bearing quebrou
